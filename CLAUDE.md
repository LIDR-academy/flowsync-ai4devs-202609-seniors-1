# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. See also [AGENTS.md](./AGENTS.md), kept as a pointer to this file for agents that look for that name instead.

## Project overview

FlowSync — a team task-management practice project. Monorepo with two independent npm projects:

- `backend/` — API on AdonisJS 7 (ESM, TypeScript)
- `frontend/` — React 19 + Vite (currently just the Vite starter scaffold; no routing/state/API-client wired up yet)

They are not linked by a workspace config — run `npm install` separately in each.

## Commands

### Backend (`backend/`)

```bash
npm install
cp .env.example .env
node ace generate:key      # writes APP_KEY into .env
node ace migration:run     # also regenerates database/schema.ts
npm run dev                # serves with HMR on http://localhost:3333
npm run build               # node ace build
npm run lint                 # eslint .
npm run format               # prettier --write .
npm run typecheck            # tsc --noEmit
npm run test                  # node ace test (Japa)
```

Run a single test file: `node ace test --files tests/functional/some.spec.ts` (unit suite lives at `tests/unit/**`, functional at `tests/functional/**`; neither directory exists yet).

### Frontend (`frontend/`)

```bash
npm install
npm run dev       # http://localhost:5173
npm run build      # tsc -b && vite build
npm run lint        # oxlint
```

Run both dev servers in separate terminals from the repo root; the backend must already be running for the frontend to call the API.

## Architecture

### Backend (AdonisJS)

- **Import aliases**: code uses subpath imports defined in `backend/package.json` `imports` (`#controllers/*`, `#models/*`, `#services/*`, `#validators/*`, `#transformers/*`, `#middleware/*`, `#database/*`, `#config/*`, `#start/*`, etc.) instead of relative paths — mirror this convention in new files.
- **`database/schema.ts` is generated** — the header says so explicitly. It's regenerated by `node ace migration:run`. Never hand-edit it; change a migration (or add a new one) and re-run migrations instead. `database/schema_rules.ts` controls how columns are typed during generation.
- **Auth has two guards** (`backend/config/auth.ts`): `api` (token-based, `@adonisjs/auth/access_tokens`, the default guard) for stateless API calls, and `web` (session-based) for browser flows. `User` (`app/models/user.ts`) composes the generated `UserSchema` with `withAuthFinder`.
- **Routes** (`start/routes.ts`) are grouped under `/api/v1`. The `auth` group (`signup`, `login`) is public; the `account` group (`profile`, `logout`) is wrapped in `.use(middleware.auth())`. Route handlers are referenced through the Tuyau-generated `controllers` registry (`#generated/controllers`), not direct imports.
- **Controller pattern**: controllers stay thin — validate the request with a VineJS validator from `app/validators/`, do the model work, then return `serialize(...)` with a `BaseTransformer` subclass from `app/transformers/` (see `UserTransformer`, `NewAccountController`, `AccessTokensController`, `ProfileController` for the shape to copy).
- **`@tuyau/core`** generates a typed route/API registry into `.adonisjs/client` on `node ace` hooks (see `adonisrc.ts`); this is what a frontend Tuyau client would consume for typed API calls, once one is wired up.
- Backend lint/format config comes from `@adonisjs/eslint-config` and `@adonisjs/prettier-config` (see `eslint.config.js` and the `"prettier"` field in `package.json`) — don't override these locally.

### Frontend (React + Vite)

- Plain Vite React-TS template as of this branch — no router, state management, or API client yet. Lint is `oxlint`, configured in `.oxlintrc.json` (React + TypeScript + oxc plugins). Formatting is `npm run format` (Prettier, config in `.prettierrc.json`); a `PostToolUse` hook in `.claude/settings.json` runs it automatically on frontend files after Write/Edit.

## Git workflow

This repo is normally worked from a personal fork, with `origin` = your fork and `upstream` = the course repo. Pull requests target `upstream` (the course repo), not `origin`. Keep that distinction in mind before pushing branches or opening PRs — don't assume `origin` is the PR target.

## Reglas de proceso

- Antes de tocar código: crear una rama nueva (`git checkout -b feat/<slug>`). Nunca commitear directo en `main`/`s1/start`.
- Al cerrar la tarea: usar la skill `/commit`, luego `gh pr create` con una descripción completa de los cambios en el cuerpo del PR.
- Después de abrir el PR: usar el subagente `adversarial-reviewer` sobre él, antes de darlo por terminado.
- No repitas ese resumen en el chat: la sesión se va a perder, el PR no. Responde solo con la URL del PR.
